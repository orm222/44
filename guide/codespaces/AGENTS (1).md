# Git 개발 작업 지침

이 문서는 이 프로젝트에서 작업하는 코딩 에이전트의 Git 작업 기준이다.
사용자의 최신 요청과 더 높은 우선순위의 지침을 따른다.

## 1. 작업 시작

- `git status`, `git branch --show-current`, `git remote -v`로 저장소 상태를 확인한다. 인증 정보가 포함된 원격 URL은 보고서에 노출하지 않는다.
- 기본 브랜치 이름은 실제 저장소에서 확인한다. 아래의 `main`은 예시이며 `master` 등으로 바꾼다.
- 기존 사용자 변경과 현재 작업의 변경을 구분한다. 기존 변경을 임의로 삭제·커밋·스태시하지 않는다.
- 사용 중인 작업 브랜치에서 이어 하는 요청이면 해당 브랜치를 계속 사용한다. 매번 새 브랜치를 만들지 않는다.
- 새 기능은 `feature/내용`, 오류 수정은 `fix/내용`처럼 목적이 드러나는 브랜치를 사용한다.
- 새 작업을 기본 브랜치에서 시작할 때, 작업 트리가 깨끗하고 원격이 있으면 `git pull --ff-only origin main`으로 동기화한 뒤 브랜치를 만든다.
- 원격이 없으면 로컬에서 진행한다. 네트워크·인증 실패와 코드 실패를 구분하고, 가능한 독립 작업은 계속한다.

## 2. 구현과 수정

- 요구사항과 완료 기준을 먼저 확인하고, 변경 범위와 검증 방법을 짧게 정리한다.
- 관련 코드와 저장소의 기존 구현 방식을 읽은 뒤 필요한 범위만 수정한다.
- 요구사항을 잘못 이해한 사실을 알게 되면 계획·구현·검증 기준을 함께 고친다.
- 병합 전 오류는 현재 작업 브랜치에서 수정하고 추가 커밋한다.
- 병합이 끝난 뒤 발견한 오류는 최신 기본 브랜치에서 `fix/내용` 브랜치를 만들어 수정한다.

## 3. 검증

- README, 프로젝트 설정, CI 설정에서 실제 테스트·정적 검사·빌드 명령을 확인한다.
- 변경에 맞는 검사를 실행한다. 오류 수정에는 가능하면 해당 오류를 재현하는 회귀 검사를 추가한다.
- 서버 동작을 변경하면 관련 요청의 정상 응답과 해당 오류 조건도 확인한다.
- 검사가 실패하면 원인을 분석하고 수정한 뒤 관련 검사를 다시 실행한다.
- 검사 도구가 없거나 실행 환경이 부족하면 실행하지 못한 항목과 이유를 명시한다. 미실행을 통과로 보고하지 않는다.
- 통과를 만들기 위해 기대값을 근거 없이 바꾸거나 실패하는 검사를 삭제하지 않는다.

## 4. 커밋

- 의미 있는 변경 단위로 커밋한다. 파일마다 커밋하거나 작은 수정마다 무조건 커밋할 필요는 없다.
- `git diff`와 `git diff --staged`로 변경을 검토한다. `git diff --check`로 공백 오류도 확인한다.
- `git add 파일경로`로 관련 파일만 추가한다. 기존에 다른 변경이 스테이징되어 있으면 그대로 커밋하지 않는다.
- 비밀키, 토큰, 실제 개인정보, 불필요한 로그·DB·빌드 결과를 커밋하지 않는다.
- 커밋 메시지는 `fix: 배차 계산에서 빈 수요 처리`처럼 변경 이유와 내용을 드러내게 작성한다.
- 정상 완료 커밋은 필요한 검증이 통과한 상태로 만든다. 사용자가 중간 저장을 요청하면 미완료·실패 상태를 명시한다.
- 커밋 직후 수정 사항을 다시 발견하면 같은 브랜치에 추가 커밋한다. 공유된 이력을 임의로 다시 쓰지 않는다.

## 5. 푸시와 PR

- 푸시·PR 생성·병합은 사용자가 승인한 작업 범위와 저장소 정책에 맞춰 수행한다. 이미 승인된 동일 범위는 다시 확인받지 않는다.
- 첫 푸시는 `git push -u origin 작업브랜치`, 이후는 `git push`를 사용한다.
- PR에는 해결한 문제, 최종 변경 내용, 실제 검증 결과, 남은 제한을 적는다.
- 강제 푸시, 보호 규칙 우회, 공유 이력 삭제는 통상 작업에 포함하지 않는다.

## 6. 병합

- PR 병합 방식과 로컬 병합 방식 중 저장소 정책에 맞는 한 가지를 선택한다.
- PR 경로에서는 필요한 CI·검토 조건을 충족한 뒤 병합하고 로컬 기본 브랜치를 동기화한다.
- 로컬 병합 경로에서는 작업 트리가 깨끗한지 확인하고 기본 브랜치를 최신으로 갱신한 뒤 작업 브랜치를 병합한다.
- 충돌이 생기면 양쪽 변경 의도를 확인하고 파일을 수정한다. 한쪽 내용을 일괄 선택하지 않는다.
- 충돌 해결 뒤 검증하고 해결 파일을 스테이징하여 병합을 완료한다.
- 병합된 결과로 필요한 검사를 다시 실행한다. 실패하면 수정·재검증 후에만 원격 기본 브랜치에 푸시한다.
- 병합이 불명확하면 현재 상태와 충돌 파일을 남긴다. 사용자 변경이 있는 상태에서 임의로 병합 취소를 실행하지 않는다.
- 작업 브랜치 삭제는 사용자 요청 또는 저장소의 정리 정책이 있을 때 수행한다.

## 7. 완료 보고

- 변경한 기능과 주요 파일을 요약한다.
- 실행한 검사와 결과, 미실행 항목을 구분한다.
- 현재 브랜치, 생성한 커밋, 푸시·PR·병합 완료 여부를 실제 결과대로 보고한다.
- 남은 문제나 작업이 있으면 구체적으로 적는다.

## 사용 안내

- 새 프로젝트라면 이 파일을 프로젝트 최상위의 `AGENTS.md`로 둔다.
- 기존 `AGENTS.md`가 있으면 기존 내용을 보존하며 필요한 규칙을 합친다.
- 이 문서는 에이전트가 따를 작업 기준이다. 필수 검사 통과를 기술적으로 강제하려면 CI와 브랜치 보호 설정도 필요하다.
- 관련 명령어와 상황별 예시는 함께 제공한 `GIT_COMMANDS_KO.md`를 참고한다.
